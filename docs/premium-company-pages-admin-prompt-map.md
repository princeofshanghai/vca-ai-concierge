# Premium Company Pages Admin MVP Prompt Map

Status: Working product and conversation specification  
Scope: Dashboard, Analytics > Content, Analytics > Visitors, and Analytics > Competitors  
Source: `VCA for PCP PRD  (1).md`, current PCP admin prototype, and the existing PCP admin PRD gap analysis

This document captures the agreed prompt framework used by the component library before approved examples are synchronized to the prototype. It defines which prompts should appear, what each prompt should ask the AI to explain, and which evidence is required.

For prompt behavior and visible prompt copy, this document supersedes the earlier `premium-company-pages-admin-agent-refresh.md`. That document remains useful as historical design rationale.

## 1. Working Model

The interaction is:

> Context → clickable prompt → AI response → evidence → navigation

- A **prompt** is a suggested request the admin can click.
- An **insight** is the grounded explanation the AI returns.
- A **navigation CTA** takes the admin to the Page, tab, section, post, or other view that contains the full supporting data.
- The MVP does not need a separate clickable insight-chip or insight-card system.
- Starter responses do not show suggested follow-up prompts. A focused contextual response may show one optional follow-up when it is the clearest continuation of the same story. In the prototype, that follow-up may be presentation-only when its purpose is to demonstrate the conversation path to stakeholders.
- Navigation is the only product action the Admin Agent performs. Recommendations remain prose; the agent does not execute them.

The Page shows evidence. A contextual prompt identifies the most valuable gap between that evidence and the understanding the admin still needs.

### Prompt copy rule

> Use the shortest unambiguous wording. Include what is known and ask for what is not known.

Rely on visible Page and time context instead of repeating it in the prompt.

Recommended:

> Why are impressions down but engagement up?

Avoid:

> Impressions fell because posting slowed.

The second example already states the AI insight and leaves little reason to click.

## 2. Prompt Types And Budgets

| Type       | Purpose                       | Appears in                    |       Budget |
| ---------- | ----------------------------- | ----------------------------- | -----------: |
| Starter    | Begin a broad briefing        | FAB hover and empty assistant | Up to 3 |
| Contextual | Investigate visible Page data | Dashboard or an Analytics tab | 0–1 per eligible section, with no more than 2 visible on a Page |

These are ceilings, not quotas. A prompt appears only when it is relevant, valuable, answerable with fresh grounded data, and not redundant with another visible prompt or prior answer.

The default prototype fixture shows all three starter prompts because Page performance, competitor, and visitor data are available. Production should show fewer than three rather than filling an unavailable slot with a weaker prompt.

Suggested follow-ups are not a third prompt type. They are optional continuations inside a response and must stay narrower than the originating contextual prompt.

## 3. Starter Prompt Framework

Starter prompts are global, curated entry points that help an admin understand what the assistant can do before they know what to ask. They are not generated by the model, triggered by a detected insight, or tailored to the Analytics Page currently in view.

The MVP starter set represents three distinct admin jobs:

| Admin job | Starter prompt |
| --- | --- |
| Review Page performance | How is my Page performing? |
| Compare the Page with competitors | How does my Page compare with competitors? |
| Understand the Page's visitors | Tell me about my Page visitors |

### How starters are determined

Every starter must:

1. Represent a frequent and important admin job.
2. Work without relying on the Page or Analytics tab currently open.
3. Demonstrate a distinct, in-scope assistant capability.
4. Be answerable with available, fresh, grounded data.
5. Produce a useful answer when performance is strong, weak, or stable.
6. Avoid assuming that a problem, cause, or opportunity already exists.

Starter prompts are intentionally broader than contextual prompts. The response, rather than the prompt wording, is responsible for identifying what matters and recommending one supported next step.

### Placement and consistency

- The empty assistant and FAB hover or focus use the same starter copy and order.
- The starter set is the same across Dashboard and Analytics Pages when the assistant opens from a general entry point.
- Starter prompts use the active managed Page and the MVP's default analysis period. They do not inherit the visible Analytics tab, date range, or filters.
- When the assistant opens from a contextual Page prompt, it runs that prompt directly and does not prepend the welcome or starter set.

The resulting mental model is:

> Starter prompts help me begin. Contextual prompts help me understand this Page.

### Availability

Three is the maximum number of starters, not a quota.

- Show the performance starter when current Page metrics are available.
- Show the competitor starter when at least one competitor is configured and comparable public data is current.
- Show the visitor starter when visitor data clears availability, privacy, and minimum-sample thresholds.
- Do not offer a starter that is expected to lead immediately to an unavailable-data response.
- Do not substitute a weaker filler prompt solely to keep three prompts visible.

### Click and session behavior

| State | Starter behavior |
| --- | --- |
| No conversation has started | Show the available starters in the empty assistant and on FAB hover or focus |
| The admin selects a starter | Open the assistant, add the selected prompt as the admin's message, and run it immediately |
| The first response appears | Remove the starter stack; unused starters do not become follow-up prompts |
| The admin minimizes and reopens the assistant | Restore the current conversation without showing the starter stack again |
| The admin starts a new conversation | Reset and show the available starter set again |
| The admin returns in a later MVP session | Show the same available starter set; prior selection does not permanently remove a starter |

### Post-MVP evolution

Future starters may become capability-aware and personalized based on account setup, available data, recent activity, and prior usage. Preserve at least one stable general entry, such as Page performance, while allowing other starter slots to be ranked or replaced.

Treat this as personalized starter behavior rather than Page-contextual behavior. Questions derived from the visible Page, tab, date range, or filters should remain contextual prompts.

## 4. Time And Freshness Policy

- Each global starter uses a predefined period that matches its source and makes the comparison reliable. Page performance uses the last seven complete days; competitor comparison uses the last 30 days.
- Analytics prompts inherit the visible Page, tab, filters, timezone, and selected date range.
- Analytics comparisons use the previous equivalent complete period unless the admin requests another baseline.
- A continued conversation keeps the current Page, filters, and time range unless the admin changes them.
- The agent never silently changes the analysis window.
- Every response exposes the analyzed period, source, and data freshness.
- If a source is older than its allowed refresh threshold, the response identifies the stale source and avoids presenting the answer as current.

Example provenance:

> July 20–26 vs. July 13–19 · Page Analytics · Data through July 26, 11:00 PM PT

The PRD's maximum analytics staleness remains `XXh` and requires an Engineering-confirmed value.

| Location        | Selected prompt                                   | Primary job                                               | Availability                                                                    |
| --------------- | ------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Empty assistant and FAB | How is my Page performing?                | Page performance briefing                                 | When Page metrics are available and a new conversation has no originating Page prompt |
| Empty assistant and FAB | How does my Page compare with competitors? | Competitive briefing                                      | When at least one competitor is configured and current public data is available |
| Empty assistant and FAB | Tell me about my Page visitors             | Audience briefing with noteworthy recent visitors         | When visitor data clears availability and privacy thresholds                    |
| Dashboard       | Why are post impressions down?                    | Explain the reach decline and recommend the next practical step | When post impressions declined and the visible Track performance data supports an explanation |
| Content         | Why are post impressions down?                    | Explain a cross-metric change                             | Only when the detected pattern is true for the selected range                   |
| Content         | What do top posts have in common?                 | Explain successful content patterns                       | When enough recent posts have comparable performance data                       |
| Visitors        | Why are Page views up but unique visitors down?   | Explain the relationship between viewing frequency and audience reach | When Page views rise while unique visitors decline for the selected range |
| Competitors     | What do trending competitor posts have in common? | Explain a shared content pattern and connect it to a Velora example | When multiple current public competitor posts support the same pattern |

### Why the Dashboard has one contextual prompt

The Dashboard already presents a seven-day performance overview, so it does not repeat the assistant's “brief me” starter or add a prompt to every section. The prototype places one contextual prompt beneath Track performance because that section contains a meaningful relationship the metrics alone do not explain:

> Why are post impressions down?

The response connects lower publishing frequency with lower reach, while noting that stronger engagement suggests the content still connects when people see it. It recommends one organic next step and presents boosting as an optional way to reach more people sooner.

## 6. Starter Prompt Specifications

### Shared starter response contract

Starter prompts are broad, so they need a brief overall assessment before narrowing to the most useful insight:

> One broad question → one overall assessment → one prioritized insight → one evidence story → one next step → one navigation destination

The overall assessment answers the starter directly. The prioritized insight explains the most important relationship behind that assessment. It is not a second, unrelated finding.

The AI should add interpretive value rather than repeat the Dashboard:

1. **Observation:** What happened?
2. **Comparison:** How is it different from the relevant prior period, segment, or Page?
3. **Relationship:** Which supported signals become meaningful when considered together?
4. **Interpretation:** What may explain the relationship, with uncertainty stated clearly?
5. **Action:** What is one realistic next step within the admin's responsibilities?

Cards carry the exact observations and comparisons. Conversational text focuses on the relationship, interpretation, and action.

When a data card immediately follows the response, the prose should usually describe direction and meaning without repeating every exact value. Include a number in the prose only when the number is itself the answer, its magnitude is essential, or no card is needed.

### Selecting the prioritized insight

Do not automatically select the largest percentage change. Rank candidate insights by:

1. **Importance:** Does it materially affect the Page or the admin's decisions?
2. **Confidence:** Is the relationship supported by sufficient, comparable evidence?
3. **Usefulness:** Does understanding it change what the admin might do?
4. **Novelty:** Does it reveal something the visible Page does not already make obvious?
5. **Actionability:** Is there a realistic next step within the MVP boundary?

The three starters use the same response logic but prioritize different relationships:

| Starter | Overall assessment | Valuable relationship |
| --- | --- | --- |
| How is my Page performing? | Improving, declining, mixed, or stable | Reach versus engagement, publishing volume versus impressions, or content patterns versus follower growth |
| How does my Page compare with competitors? | Ahead, behind, or mixed | Page-versus-competitor differences in growth connected with publishing frequency, engagement, topic, or format |
| Tell me about my Page visitors | Current audience makeup and direction | Leading audience group connected with noteworthy recent visitors |

Reject responses that are:

- a list of metrics the admin can already see,
- an unsupported causal diagnosis,
- a miniature report containing several unrelated findings,
- or a generic recommendation that is not connected to the evidence.

### S1. How is my Page performing?

**Admin need**

The admin wants a useful performance briefing without reading and manually combining the Dashboard and Content Analytics views.

**Expected AI insight**

Summarize the overall direction of Page performance, then explain the most useful supported relationship across reach, engagement, follower growth, publishing volume, and content. Use competitor or visitor information only when it is necessary to explain that Page-performance story; leave a full competitor or visitor briefing to the other starters. Do not manufacture a problem when performance is stable.

Illustrative response shape; final numbers must match the approved prototype fixture:

> Overall, Velora's content connected better with people who saw it, but it reached fewer people this week. You posted less often, which likely contributed to the drop in impressions even as engagement improved.

After the `Summary` card, bridge from the evidence to the Post entity:

> Try posting one more time this week using a topic that already worked. Your top post below is a good place to start.

Use calibrated language such as “the clearest pattern” or “likely contributed” when the evidence shows correlation rather than verified causality.

**Required evidence**

- Page metric trends for the last seven complete days and previous seven
- Ranked content performance for the same period
- Precomputed deltas and rankings rather than model arithmetic over raw rows

**Response presentation**

- A concise opening with the overall assessment and the most useful relationship
- One `Summary` Metric data card with the visible context `Last 7 days`
- Current metric values with right-aligned deltas; do not show previous-period raw values
- One short recommendation between the `Summary` card and the supporting Post entity
- One optional untitled Post entity card when a concrete example supports the recommendation
- Use the Post card's read-only evidence presentation: retain passive engagement counts and `View post`, but do not show the three-dot management menu
- Compact provenance available without adding analytical detail to the visible card
- No more than one data card and one entity card in the initial view

Illustrative `Summary` card fixture:

| Current value | Metric | Right-aligned delta | Tone |
| --- | --- | --- | --- |
| 42.8K | Impressions | Down 18% | Negative |
| 7.4% | Engagement rate | Up 28% | Positive |
| 3 | Posts published | Down 2 | Negative |

The visible card does not say `vs previous 7 days`. The underlying comparison and provenance still use the previous equivalent complete seven-day period.

**Navigation destination**

When the Post entity is present, use its natural `View post` action as the navigation destination. Do not add a competing response-level CTA. Do not draft, publish, boost, message, or initiate outreach.

For the current scripted prototype, `View post` is a representational CTA and does not need to open a working destination.

**Stable-state behavior**

If no meaningful change qualifies:

> Page performance was generally stable over the last seven days. Reach and engagement stayed close to the previous period, and no content change needs immediate attention.

### S2. How does my Page compare with competitors?

**Admin need**

The admin wants a concise competitive briefing without manually scanning each tracked Page.

**Expected AI insight**

For MVP, treat every configured competitor as part of the admin's intended comparison set. State whether the Page is ahead, behind, or mixed across the Pages shown, then explain the most meaningful supported relationship involving follower growth, posting frequency, or response per post. Do not select one competitor to stand in for the group.

Illustrative response shape; final numbers must match the approved prototype fixture:

> Overall, Velora's follower growth is slower than the Pages shown in this comparison. Over the last 30 days, those Pages also posted more often and generally got more response per post.

Before the evidence card:

> Before posting more often, review trending competitor posts on topics Velora also covers to see what earns a stronger response.

Do not claim that posting frequency or reactions caused follower growth. The evidence supports a relationship, not a causal conclusion.

**Required evidence**

- The complete configured competitor set
- New followers, posts published, and reactions for Velora and every configured competitor over the same 30-day period
- Precomputed average reactions per post for each Page
- Trending public competitor posts from the current source window
- Per-source freshness

**Response presentation**

- A concise group-level assessment and one relationship in prose
- One `Compare` card titled `New followers`
- `Last 30 days` as the visible card context
- One Page per row: every tracked competitor plus Velora
- One scalar new-follower value per row; no follower total, post count, delta, or second metric in the row
- Velora appears first using the component's existing `You` highlight; tracked competitors follow in descending new-follower value
- Compare bars use the same standalone neutral-gray treatment as Visitor demographics: no background track, a shared left baseline for nonnegative values, and lengths scaled to the largest value shown
- One next-step sentence immediately before the card
- One secondary `View trending competitor posts` action in the card footer
- No individual competitor entity card and no suggested follow-up prompts in the initial response

**Navigation destination**

Use one `View trending competitor posts` action inside the Compare card footer. Do not recommend a specific format as the winner, generate a post, or publish content.

**Unavailable-state behavior**

If no competitors are configured, explain the limitation and deep-link to competitor setup. If competitor data is stale, identify the stale source and avoid a current comparison.

### S3. Tell me about my Page visitors

**Admin need**

The admin wants an audience briefing without reading demographic tables.

**Expected AI insight**

Summarize the clearest current audience pattern, then make it concrete with up to three recent visitors who have meaningful Page activity. The aggregate summary and the named visitors must support the same audience story. Do not treat a small set of people as proof of the overall pattern.

Illustrative response shape:

> Most of your Page visitors come from three industries: Retail, Hospitals and Health Care, and Technology, Information and Internet. Together, they made up 63.3% of visitors over the last 30 days.
>
> Retail is the largest group, and one of your stronger posts features a retail customer. This does not prove the post brought those visitors to your Page, but it gives you a useful topic to test again.
>
> Try one more post for benefits teams in retail, then compare it with your broader posts.
>
> A few recent visitors from these industries also came back or viewed more than one post. Take a look below to learn more about them.

Do not say that visitors match the Page's target audience unless a permitted, explicit target-audience definition is available.

**Required evidence**

- Industry demographics for the default period, calculated from unique visitors
- The current LinkedIn industry taxonomy labels. In production, resolve these from stable taxonomy identifiers.
- Named visitor profiles and recent Page activity, when permitted
- Privacy and minimum-sample checks

**Response composition**

- One concise overall assessment
- One `Summary` Metric card showing `Last 30 days`, the three leading industry shares, and `Other` as the combined remainder
- One short bridge connecting the pattern to a cautious content test and explaining why the people below are shown
- One Person rail with up to three visitors
- No suggested follow-up prompts and no separate response-level CTA

**Named visitor selection**

- Show no more than three visitors in the initial response.
- Select visitors from the industries named in the aggregate insight so the rail supports the same story.
- Prioritize meaningful Page activity, such as returning or viewing more than one post.
- Use recency as a secondary signal.
- Treat named visitors as examples, not proof of the aggregate pattern.
- If person-level identity is unavailable, omit the rail without weakening the industry summary.

**Industry interpretation rules**

- Use the exact LinkedIn industry label in structured UI. Store the taxonomy identifier in a production system so a label update does not break the underlying segment.
- Say `most visitors` only when the combined share is greater than 50%. Otherwise, say `the largest visitor groups`.
- In this compact Summary card, `Other` is a derived rollup of every industry outside the three named groups. It is not the same as the native `Others` row in the full analytics table.
- Do not claim that a post caused the industry mix. A related strong post can support a content test, but the response must state that the relationship is not proof.
- Recommend one test rather than telling the admin to change their entire content strategy.
- Do not fill an empty slot with a visitor who has only a weak or generic signal.
- Do not call these people leads, prospects, high-intent visitors, or likely buyers.

**Navigation destination**

Use `View profile` on each Person card as the single navigation goal. Do not add a competing `View visitor analytics` action, assign consideration stages, message visitors, or draft outreach.

**Unavailable-state behavior**

If named visitor information is unavailable, return the aggregate audience summary without a Person rail. If volume is below a privacy or minimum-sample threshold, state that there is not enough data for a reliable audience breakdown and deep-link to the available visitor view.

## 7. Content Prompt Specifications

### C1. Why are post impressions down?

**When it appears**

Only when impressions declined for the selected range while one or more engagement measures increased or remained meaningfully strong.

**Expected AI insight**

Explain the cross-metric pattern instead of repeating either metric. Identify the strongest supported driver, such as lower posting frequency or a smaller number of posts, and separate observation from inference.

Example using the current prototype fixture:

> Velora published three posts in the last 7 days, two fewer than the week before. That likely contributed to lower impressions because people had fewer chances to see the content. Engagement improved, so the posts still connected with people who saw them. Try publishing one more post this week. If faster reach matters, consider boosting the strongest recent post.

**Required evidence**

- Impressions and engagement trends
- Posting count and timing
- Post-level performance
- Previous equivalent period

**Navigation destination**

Open the strongest recent post through its `View post` action. The response may recommend an organic step and explain boosting as an optional paid step, but it does not draft, publish, or boost automatically.

**Prototype evidence treatment**

- Do not add a data card when the response launches directly from Track performance because the visible Page metrics already provide the baseline evidence.
- Show the strongest recent Post entity to make the optional boost recommendation concrete.
- Keep `View post` as the entity CTA. Do not replace it with a boost action.
- Show one clickable follow-up, `How do I boost this post?`, after the entity card.
- When selected, append the follow-up as a user message and provide one text-only
  assistant response explaining the existing Page admin steps.
- State that the assistant cannot launch the boost from chat. Goal, audience,
  budget, schedule, and billing remain under the admin's control.
- Place one `Sources` block below the explanation with the LinkedIn Help article
  about boosting a Page post. Do not add another suggested follow-up.

### C2. Which content is working best?

**When it appears**

In the Post performance section when at least two recent posts have comparable
performance data and lead on different meaningful outcomes.

**Expected AI insight**

Explain that the answer depends on the admin's goal, then identify the strongest
post for each supported outcome. Connect the results to a useful content choice
without implying that one post format will always win.

Example using the current prototype fixture:

> What is working best depends on what you want people to do. The Arbor customer
> story earned the strongest engagement rate, while the carrier-readiness post
> had the highest click rate. Use these as a starting point, then test a real
> customer challenge with one clear takeaway or resource.

**Required evidence**

- Ranked recent posts
- Engagement rate
- Click rate
- Post topic and format
- A sufficient number of comparable recent posts

**Prototype evidence treatment**

- Do not add a data card. The concrete evidence is the post itself.
- Show the two posts in one horizontal Post entity rail.
- Give each Post card one neutral result tag that explains why it was selected,
  with the exact metric directly beside it.
- Keep each Post card read-only and use `View post` as the repeated entity action.
- Do not add a suggested follow-up prompt or a second assistant response.
- Put one concise recommendation after the rail.

**Navigation destination**

Use `View post` on each entity. The repeated actions share one navigation goal.
Do not generate a draft, start a post, or add another follow-up action.

## 8. Visitor Prompt Specifications

### V1. Why are Page views up but unique visitors down?

**When it appears**

When Page views increased and unique visitors decreased over the selected period compared with the previous equivalent period.

**Expected AI insight**

Explain that the Page received more views from fewer distinct people. Describe increased repeat viewing as a possibility rather than a confirmed cause.

Example response shape:

> Your Page is getting more views from fewer people. Some visitors may be returning more often, even though fewer distinct people are reaching your Page.

**Required evidence**

- Page views for the selected and previous equivalent periods
- Unique visitors for the selected and previous equivalent periods
- The average Page views per unique visitor for the selected period

**Prototype evidence treatment**

- Do not add a data card. The source metrics are already visible beside the contextual prompt.
- Include the two deltas in one concise evidence sentence.
- Do not claim that returning visitors caused the pattern. Present repeat viewing as a possible interpretation.
- Recommend adapting a proven content approach for a different customer or business problem, then give a clear period for evaluating whether unique visitors improve.
- Show the Arbor customer story as a read-only Post entity after the response. Treat it as an example to build from, not as the cause of the visitor pattern.

**Navigation destination**

Use `View post` on the supporting Post entity. Do not add a response-level destination CTA.

### Post-MVP visitor candidates

- `How has my visitor mix changed?` requires current and previous demographic periods that clear privacy and minimum-sample thresholds.
- `Which visitor groups engage most with my content?` requires a reliable aggregate join between visitors and engagers.

## 9. Competitor Prompt Specifications

### K1. What do trending competitor posts have in common?

**When it appears**

When multiple current public posts from the Pages in the selected comparison support the same content pattern.

**Expected AI insight**

Identify a shared topic, structure, or content approach across the trending posts. Explain whether the pattern appears across different formats so the response does not incorrectly name one format as the winner. Connect the pattern with one Velora post only when Velora's performance data supports that comparison.

Example using the current prototype fixture:

> The posts use different formats, but they follow a similar approach. Each one starts with a specific benefits operations problem and gives people a practical takeaway. That suggests the clear problem and practical value matter more than one particular format.

**Required evidence**

- Trending public competitor posts from the selected 30-day period
- Post content and format
- Public engagement measures
- Velora's ranked posts and click-rate data

**Prototype evidence treatment**

- Place the single contextual prompt beneath `Trending competitor posts`.
- Do not repeat the competitor comparison or the visible competitor Post cards in chat.
- Explain the pattern in prose and avoid claiming that it caused the posts' performance.
- Show Velora's carrier-readiness post as the concrete example because it follows part of the pattern and earned Velora's highest click rate.
- Keep the Post entity read-only and use `Highest click rate` as the result tag.
- Do not add a data card, response-level CTA, or suggested follow-up.

**Navigation destination**

Use `View post` on the supporting Velora Post entity. Do not copy, draft, publish, or boost content.

## 10. Visitor Data Boundary

The stakeholder MVP assumes the Admin Agent can identify and rank relevant Page visitors. Relevance is based on target-audience fit and recent Page activity. It is not a claim of buying intent.

| Visitor capability                                        | PRD tool support                                                                                  | MVP status                                                           |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Aggregate visitor demographics                            | Supported by Get Audience                                                                         | Approved                                                             |
| Audience composition over time                            | Supported by Get Audience with date range                                                         | Approved when comparable periods and sample thresholds are available |
| Compare visitors with engagers                            | Supported by Get Audience segments plus Compare                                                   | Approved                                                             |
| Named visitor list                                        | Prototype assumption; production tool contract still required                                     | Approved for the stakeholder MVP                                     |
| Individual repeat visits or viewed-post history           | Prototype assumption; production tool contract still required                                     | Approved as a relevance signal                                       |
| Individual relevance ranking                              | Prototype assumption; production scoring and explanation contract still required                  | Approved when each result explains why it ranked                     |
| Consideration-stage or “high intent” classification       | Not defined and risks overstating weak behavioral evidence                                        | Exclude                                                              |
| Target-audience match                                     | Requires an explicit, permitted target-audience definition                                        | Approved as an MVP assumption                                        |
| Attribute a specific demographic group to a specific post | No post-to-demographic join is defined                                                            | Hold                                                                 |
| Diagnose custom-button performance                        | Custom-button clicks and Page configuration evidence are not explicit in the current tool schemas | Hold                                                                 |
| Message, reply to, or draft outreach for a visitor        | Explicitly out of scope                                                                           | Exclude                                                              |

### Resulting visitor decision

For the current admin MVP:

- Allow aggregate audience composition and visitor-versus-engager comparisons.
- Allow named visitor ranking using audience fit and recent Page activity.
- Explain the evidence behind each ranked visitor.
- Deep-link to the visitor analytics view for exploration.
- Do not present relevance as buying intent or consideration stage.
- Do not recommend or initiate outreach.

Production implementation still needs an explicit person-level tool contract with:

- permitted person-level fields,
- activity types and retention window,
- privacy and visibility rules,
- minimum evidence for ranking,
- explanation of why a person was ranked,
- freshness and source,
- role and entitlement checks,
- prohibited intent claims and actions.

## 11. Shared AI Insight Contract

All admin responses follow the shared [PCP AI response formatting rules](./premium-company-pages-vca/ai-response-formatting.md). This contract defines what the response communicates; the formatting rules define how that content is presented consistently across admin and member/visitor experiences.

The default response model for a focused contextual prompt is:

> One prompt → one question → one primary insight → one evidence story → one navigation destination

Broad starter prompts use the expanded starter response contract in Section 6:

> One broad question → one overall assessment → one prioritized insight → one evidence story → one next step → one navigation destination

A response may contain multiple facts when they work together to support one conclusion. It should not combine unrelated content, visitor, and competitor observations into one causal story.

Every selected prompt should produce:

1. **Opening assessment or insight:** One to three sentences that answer the question directly.
2. **Evidence:** One or two focused cards or views that carry the detailed proof.
3. **Provenance:** A simple visible period plus Page, exact range, comparison basis, source, and freshness available through the supporting provenance treatment.
4. **Recommendation:** One prioritized organic suggestion in prose when the evidence supports it. A clearly secondary paid option may follow when it addresses the same goal and is not framed as necessary.
5. **Navigation:** One primary navigation goal. A natural entity action such as `View post` may serve as that destination.

Starter responses do not show suggested follow-up prompts. A focused contextual response may show one concise follow-up when it directly continues the same question. The composer remains available for any other continuation.

The response must:

- distinguish observed facts from inferred explanations,
- avoid model arithmetic over raw rows,
- state missing, partial, stale, or incomparable data,
- avoid repeating every metric already shown in evidence cards,
- remain within organic Page performance, audience, content, reporting, and competitor decisions,
- refuse or redirect automatic drafting, publishing, boosting, messaging, outreach, and unsupported person-level claims. The assistant may explain how a supported product action works without performing it.

### Broad starter rule

Each starter should form one coherent story rather than a comprehensive report. It should:

- lead with the overall assessment of the subject,
- explain one prioritized relationship behind that assessment,
- avoid combining unrelated findings into one causal explanation,
- visually support only that relationship in the initial response,
- and navigate to the view containing its strongest supporting evidence.

A starter response should not become a miniature dashboard or render a separate rich card for every potentially relevant metric.

## 12. Rich UI Evidence Framework

Rich UI cards are evidence for the AI insight, not miniature dashboards and not a second explanation layer.

The governing rule is:

> One card = one evidence relationship.

A card may show several data points when their relationship creates the meaning. A trend can contain many points, a comparison can contain several companies, and a content list can contain several posts. A card becomes overloaded when its values support unrelated conclusions or make the admin decide which number matters.

### Four evidence jobs

| Evidence job | Question it answers                              | Preferred pattern             |
| ------------ | ------------------------------------------------ | ----------------------------- |
| Change       | What changed, and when?                          | One metric with its trend     |
| Difference   | How do periods, segments, or companies compare?  | Comparison                    |
| Makeup       | Who or what makes up this audience?              | Audience breakdown            |
| Examples     | Which posts or entities support the explanation? | Ranked content or entity list |

Choose the evidence job before choosing a UI component. Component names such as `Metric`, `MetricWithTrend`, `Compare`, `AudienceFit`, and `ContentList` are implementations of these jobs, not separate product concepts the admin needs to understand.

### Response limits

- Lead with one primary insight.
- For starter responses, default to one data card and add no more than one supporting entity card.
- Use no more than three rows or items in a comparison, breakdown, or list before navigating to the full view.
- Give every scoped data card one visible time range. The standard comparison basis for its deltas may remain in the provenance details rather than the visible header.
- Use one primary navigation CTA.
- Do not repeat every card value in the prose.
- Additional evidence belongs in a continued conversation or on the destination Page.

### Card inclusion test

Before adding a value, row, or item to a card, ask:

1. Does it help prove the card's one evidence relationship?
2. Does it use the same time range and comparison basis?
3. Does the AI explanation make clear why it matters?
4. Would removing it weaken the conclusion?

If removing it would not weaken the conclusion, leave it out.

### Data cards and entity cards

- A **data card** proves why the AI reached its conclusion.
- An **entity card** shows which post, company, or other object the admin can inspect.
- A data card may use a simple visible title such as `Summary`; its internal evidence job does not need to appear in the UI.
- A data card shows current values and deltas by default. Do not add previous-period raw values unless the conclusion cannot be understood without them.
- The AI response introduces why a single entity appears. The entity card does not need an additional visible title.
- When several entities appear, use one short group label outside the cards rather than repeating a title inside each card.
- A standalone entity card fills the available assistant response width. Entity cards in a horizontal rail stay compact so multiple items remain easy to scan.
- Entity cards primarily support navigation and should not become secondary analytics dashboards.

### Examples

For `How is my Page performing?`:

1. A `Summary` Metric card shows `Last 7 days`, current impressions, engagement rate, posts published, and their right-aligned deltas.
2. A short recommendation connects that evidence with one top Post entity.
3. The Post card uses the read-only evidence presentation, with no three-dot management menu.
4. The Post card's `View post` action is the navigation destination; do not add a competing response-level CTA.

For `Why are post impressions down?` when launched from Dashboard Track performance:

1. Do not repeat the visible Track performance metrics in a data card.
2. Explain the relationship between fewer posts, lower impressions, and stronger engagement in plain language.
3. Show the strongest recent Post entity as the concrete example.
4. Keep `View post` as the navigation destination.
5. A clickable `How do I boost this post?` follow-up appends the user's
   question and a text-only explanation of the existing Page admin flow.
6. State that the assistant cannot launch the boost from chat, then show the
   relevant LinkedIn Help article in a `Sources` block. Do not add another
   suggested follow-up.

For `What do top posts have in common?`:

1. An Examples card shows the two posts that support the pattern.
2. `View top posts` navigates to the filtered content table.

For `Why are Page views up but unique visitors down?`:

1. Do not repeat the visible Visitor highlights metrics in a data card.
2. Explain the relationship between higher Page views and fewer unique visitors in plain language.
3. Describe repeat viewing as a possible interpretation, not a confirmed cause.
4. Recommend adapting the proven customer-outcome approach for a different customer or business problem.
5. Show the Arbor customer story as the concrete example, with `View post` as its only action.

For `What explains the follower-growth gap?`:

1. A Difference card compares follower growth and publishing frequency.
2. An Examples card shows up to two representative competitor posts.
3. `View competitor comparison` navigates to the full comparison.

### Current card pressure tests

- A monthly summary containing unrelated visitors, new followers, and follower-total metrics behaves like a miniature dashboard. Use it only for an explicitly requested overview, not as evidence for a focused insight.
- An audience card should answer one audience question. Avoid combining target match, composition, change, intent, and content attribution in the same card.
- A conversion-path card is valid when the question is specifically about progression or drop-off, but custom-button data and configuration evidence must be confirmed before it enters the approved MVP prompt map.
- A content list is useful when every included post supports the same content pattern. Otherwise, show fewer posts or split the analysis.

The intended division of labor is:

> The Page holds the full data. The AI explains what to notice. The data card provides the proof. An optional entity card makes it concrete. The CTA lets the admin inspect the source.

## 13. Selection And Suppression Rules

When multiple contextual prompts qualify:

1. Prefer the prompt tied to the largest meaningful and sufficiently sampled change.
2. Prefer a cross-metric or cross-source interpretation gap over a question that repeats one visible metric.
3. Prefer a prompt that leads to an allowed decision or focused evidence view.
4. Suppress prompts already answered in the visible conversation.
5. Suppress prompts dismissed or shown too recently.
6. Show no prompt when the data is stable, insufficient, stale beyond threshold, or already self-explanatory.

The MVP prototype can use scripted fixtures, but those fixtures should behave as though these rules exist.

## 14. Decisions Still Requiring Product Or Engineering Confirmation

The stakeholder MVP assumes person-level visitor relevance and target-audience fit. Production implementation still requires confirmation of:

1. Whether person-level visitor identity and activity are approved and retrievable.
2. Whether a Page-defined target audience exists and can be used by the agent.
3. Whether custom-button clicks and Page CTA configuration are available to tools.
4. The minimum sample and privacy thresholds for audience breakdowns.
5. The maximum freshness threshold represented by `XXh`.
